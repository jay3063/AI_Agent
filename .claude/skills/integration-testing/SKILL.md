# 소프트웨어 통합시험 스킬

## 0. 템플릿 및 테스트 베이시스 확인 (최우선)

- `references/template.md`를 연다. 실제 공식 템플릿은
  `WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/TPL-SWE5-001/002/003`
  이며, 이 마크다운은 그 목차/열 구성을 그대로 반영한 작업용 사본이다(PLACEHOLDER 아님). 산출물의 섹션/열 구성은 이 순서를 그대로 따른다.
- **테스트 베이시스**는 반드시 다음 두 가지다 — 임의로 시험 케이스를 만들지 않는다.
  1. 아키텍처 설계서(`architecture-design` 스킬 산출물)의 **인터페이스 명세**(6장) — 모든 내부/외부 인터페이스가 시험 대상이다.
  2. 아키텍처 설계서의 **통합 순서**(11장 통합 전략/순서 테이블) — 통합시험은 이 순서를 그대로 따른다.
- `Skill` 도구로 `test-design-techniques` 스킬도 함께 로드한다. 시험 케이스 도출 기법(동등분할/경계값분석/오류추정 등)의 명칭·정의는 그 스킬의 공통 카탈로그를 따르며, 이 스킬에서 재정의하지 않는다.
- 위 산출물이 없거나 상세설계(`detailed-design` 스킬 산출물)와 모순되면 추측하지 말고 사용자에게 알린다.

## 1. 통합 원칙 및 항목/순서 정의 (템플릿 2~3장)

1. 아키텍처의 통합 순서 테이블을 그대로 가져와 통합 항목 ID, 선행조건, 의존성, 순서, 담당, 계획 베이스라인을 정리한다. 순서를 임의로 재배열하지 않는다 — 재배열이 필요하면 불일치로 보고한다.
2. 통합 단계, 위험 우선순위(ASIL이 높은 인터페이스 우선), 반복 가능성, 실패 격리 원칙을 정의한다.

## 2. 환경/형상, 진입·종료 기준 (템플릿 4~5장)

진입/종료 기준에는 **함수 커버리지 100%, Call 커버리지 100%, 테스트 성공률 100%**를 포함한다(달성 전 해당 통합 단계를 종료 처리하지 않는다). 테스트 성공률 100%는 CLAUDE.md 통합 테스트 지침의 게이트이며, 실행한 모든 통합시험 케이스가 Pass여야 한다는 뜻이다(Fail/Blocked가 남아 있으면 종료할 수 없다).

## 3. 시험 기법 선정 (필수, 템플릿 7장)

`references/iso26262-test-methods.md`를 따른다.

1. 모든 인터페이스에 **요구사항기반 시험 + 인터페이스 시험**을 적용한다(생략 불가).
2. 대상 인터페이스/통합 항목이 파생된 안전요구사항의 ASIL을 확인하고, ASIL에 따라 **결함주입 시험**(아키텍처 9장 오류 격리와 연계), **자원사용 시험**(아키텍처 13장 자원/배포 경계와 연계)의 비중을 조정한다.
3. 모델 기반 개발을 사용하는 경우 **백투백 비교 시험**을 추가한다.
4. 각 시험 케이스는 케이스 도출 기법(요구사항분석/동등분할/경계값분석/오류추정)을 함께 명시한다 — `tdd` 스킬의 `@technique` 어휘와 동일한 명칭을 사용해 전 단계 일관성을 유지한다.

## 4. 통합시험 케이스 작성 (템플릿 6장, TPL-SWE5-002)

각 케이스에 Test ID, Trace(인터페이스 ID/통합 항목 ID/요구사항 ID), Integration Item, Stimulus, Expected Result(인터페이스 계약 기준), Technique(1절+3절 조합), Automation 여부를 기록한다. 인터페이스 계약(사전/사후조건, 오류 계약)에 없는 기대 결과를 임의로 만들지 않는다.

## 5. 시험 실행 — 통합 순서를 따라 진행 (필수)

1. 통합 순서 테이블의 순서대로 시험을 실행한다. 선행 항목이 통과하기 전에는 후행 항목을 시험하지 않는다. 필요한 스텁/드라이버는 순서 테이블에 정의된 대로 사용한다.
2. 실행 결과를 TPL-SWE5-003 형식(Result/Actual Result/Evidence Locator/Defect ID/Disposition, Run 요약)으로 기록한다.
3. 실패/편차는 분류·보고·재시험·승인 절차(템플릿 10장)에 따라 처리한다. **테스트 성공률 100%**(CLAUDE.md 통합 테스트 지침)가 될 때까지 결함 수정 → 재시험을 반복한다. Fail 케이스를 "허용 가능한 편차"로 임의 처리하고 완료로 보고하지 않는다.

## 6. 구조적 커버리지 측정 — 함수 커버리지/Call 커버리지 100% (필수)

`references/coverage-and-tools.md`를 따른다. 측정 없이 "100% 달성"이라고 서술하지 않는다.

1. `coverage.py` + `ast` 교차 검증으로 **함수 커버리지**를 측정한다. 미커버 함수가 있으면 그 함수를 진입시키는 케이스를 추가하고 재측정한다.
2. 표준 라이브러리 `trace` 모듈(`countcallers`)로 실제 실행된 호출 엣지를 기록하고, 아키텍처/상세설계에 **선언된 호출 엣지**와 비교해 **Call 커버리지**를 측정한다. 선언되었으나 실행되지 않은 엣지는 케이스를 추가해 메운다. 실행되었으나 선언되지 않은 엣지는 설계-구현 불일치로 별도 보고한다.
3. 두 지표 모두 100%가 될 때까지 3~5절을 반복한다. "거의 100%"를 완료로 보고하지 않는다.

## 7. 회귀 전략 / 적용 한계 (템플릿 9, 12장)

변경 영향에 따른 회귀 대상 선정 기준과 자동 실행 방법을 정의하고, 통합시험으로 확인할 수 없는 범위(시스템/HIL/차량/양산 환경)를 명시한다.

## 8. 추적성 (템플릿 11, 13장)

아키텍처 인터페이스 ↔ 통합 항목 ↔ 시험 케이스 ↔ 실행 결과 ↔ 결함 간 양방향 추적성을 확립한다. 매핑되지 않는 인터페이스, 시험되지 않은 통합 항목을 모두 보고한다.

## 9. A-SPICE / ISO 26262 자체 점검 (필수)

`references/aspice-iso26262-checklist.md`를 따라 A-SPICE SWE.5 BP1~BP8과 ISO 26262-6 통합시험 관련 항목을 자체 점검하고, 문서 최종 섹션에 별도로 제시한다.

## 출력물 구성 (TPL-SWE5-001/002/003 순서 준수)

1. 문서 통제(작성/검토/승인 상태, 변경 이력)
2. 목적 및 적용범위 ~ 적용 경계
3. 통합 원칙
4. 통합 항목과 순서(아키텍처 통합 순서 그대로 계승)
5. 환경 및 형상
6. 진입 및 종료 기준(커버리지 100% 포함)
7. 통합시험 케이스 요약 + TPL-SWE5-002 케이스 시트
8. 시험 설계기법(ISO 26262-6 근거)
9. 실행 및 결과 기록 규칙 + TPL-SWE5-003 결과/실행요약 시트
10. 회귀 전략
11. 실패 및 편차 처리
12. 추적성과 보고
13. 적용 한계
14. 추적성
15. 참고자료
16. 구조적 커버리지(함수/Call) 측정 결과
17. A-SPICE SWE.5 / ISO 26262-6 자체 점검 결과

## 원칙

- 시험 케이스는 아키텍처 인터페이스 명세와 통합 순서라는 테스트 베이시스에서만 도출한다. 베이시스에 없는 임의 케이스를 추가하지 않는다.
- 통합 순서를 건너뛰거나 재배열하지 않는다.
- 함수 커버리지/Call 커버리지 100%, 테스트 성공률 100%는 선택 사항이 아니라 **필수 게이트**다. 실제 도구·실행 결과 없이 완료로 보고하지 않는다.
- 본 스킬은 실무 보조 도구이며 Automotive SPICE PAM, ISO 26262 원문을 대체하지 않는다는 점을 산출물에 명시한다.
- 산출물은 사용자가 사용한 언어(기본: 한국어)로 작성한다.

## 경계 (이 스킬이 다루지 않는 것)

- **함수 계약 하나의 화이트박스 단위시험은 다루지 않는다.** 그것은 `tdd` 스킬(`coding` 에이전트)의 몫이며, 이 스킬은 그 결과(단위시험 통과)가 전제된 상태에서 컴포넌트 간 상호작용만 다룬다.
- **SW 요구사항 전체에 대한 블랙박스 시스템/자격 시험은 다루지 않는다.** 그것은 `sw-system-test` 스킬(`sw-system-tester` 에이전트)의 몫이며, 그 스킬은 아키텍처 내부 구조를 보지 않고 SW 요구사항 명세서만을 테스트 베이시스로 삼는다.
- 구조적 커버리지 목표는 **함수 커버리지·Call 커버리지(아키텍처 수준)만** 다룬다. 단위 수준 statement/branch 커버리지나 시스템 수준 요구사항 커버리지는 이 스킬의 게이트가 아니다.
