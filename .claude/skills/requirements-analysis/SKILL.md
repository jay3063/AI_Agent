# 요구사항 분석 스킬

## 0. 템플릿 확인 (최우선)

- `references/template.md`를 연다. 이 파일은 **잠정(placeholder) 양식**이며, 사용자가 실제 템플릿을 제공하면 이 파일 하나만 교체하면 된다.
- 만약 `references/template.md` 상단에 "PLACEHOLDER" 표시가 남아 있다면, 산출물 서두에 "⚠ 확정 템플릿 미반영 — 임시 양식 사용 중"이라고 반드시 명시한다. 임의로 템플릿을 확정된 것처럼 다루지 않는다.
- 실제 템플릿이 반영된 뒤에는 이 경고 없이 해당 템플릿의 섹션/필드/명명규칙을 그대로 따른다.

## 1. 요구사항 분류

각 요구사항 작성 전, 아래를 먼저 판단하고 기록한다.

| 구분 | 판단 기준 |
|---|---|
| 레벨 | Stakeholder(이해관계자) / System(SYS.2) / Software(SWE.1) |
| 유형 | 기능(Functional) / 비기능(Non-functional) |
| 안전 관련 여부 | 안전목표(Safety Goal)에서 파생되는가 → 그렇다면 ISO 26262 대상, ASIL 부여 필요 |

## 2. 기능 요구사항 작성

1. 요구사항 문장은 `<주체> shall <조건> <행위> <성능/정확도 기준>` 형태의 능동태 단일 문장으로 작성한다 (`references/clarity-checklist.md` 준수).
2. 상호작용/행위를 다이어그램으로 표현한다 — 어떤 다이어그램을 쓸지는 `references/uml-sysml-guide.md`의 매핑표를 따른다. 다이어그램은 Mermaid 코드 블록으로 산출물에 삽입한다 (렌더링 가능해야 함).
3. SysML Requirement Diagram 표기(«derive», «satisfy», «verify», «trace», «refine»)를 이용해 상위 요구사항과의 관계를 다이어그램에도 반영한다 — 이는 4번 추적성과 직결된다.

## 3. 비기능 요구사항 작성

1. `references/iso25010.md`의 8대 품질특성(기능적합성/성능효율성/호환성/사용성/신뢰성/보안성/유지보수성/이식성) 중 해당하는 것을 태깅한다.
2. 각 요구사항에 정량적 기준(수치, 단위, 조건)을 명시한다. "적절히", "충분히", "빠르게" 같은 정성적 표현만 있는 문장은 반려하고 재작성한다.
3. **검증방안은 반드시 실행 가능해야 한다.** 다음 셋 중 하나를 만족하지 못하면 반려 후 재작성한다.
   - 구체적 방법/도구가 존재한다 (예: 부하테스트 도구, 정적분석 도구, 표준화된 설문/척도)
   - 합격/불합격 판정 기준(임계값)이 정량적으로 정의되어 있다
   - 현재 프로젝트 환경에서 실제로 수행 가능하다 (존재하지 않는 장비/불가능한 조건 전제 금지)
   - 예시는 `references/iso25010.md`의 "검증방안 예시" 표를 참고한다.

## 4. 추적성 부여 (양방향)

`references/traceability-and-consistency.md`의 ID 체계와 추적 매트릭스 형식을 따른다.

1. 모든 요구사항에 고유 ID를 부여한다 (예: `SYS-REQ-004`, `SW-REQ-012`, `NFR-SEC-003`).
2. 모든 요구사항 레코드에 **Upstream(상위 출처)**, **Downstream(하위 산출물/검증 항목)** 필드를 채운다. 아직 하위 산출물이 없으면 "TBD"로 명시하되 필드 자체를 생략하지 않는다.
3. 요구사항을 신규/수정할 때마다 중앙 추적 매트릭스(`traceability-matrix.md`, 산출물 디렉터리에 생성)를 함께 갱신한다. 매트릭스 갱신 없이 요구사항만 추가하지 않는다.

## 5. 일관성 검증

1. 프로젝트 용어집(`glossary.md`, 없으면 이번 작업에서 생성)과 용어를 대조해 동일 개념에 다른 용어를 쓰지 않았는지 확인한다.
2. 요구사항 간 모순(같은 조건에서 다른 결과를 요구하는 경우), 중복(동일 내용 다른 ID) 여부를 스캔한다.
3. 발견된 문제는 별도 "일관성 점검 결과" 섹션에 근거(요구사항 ID 쌍)와 함께 보고한다. 조용히 넘어가지 않는다.

## 6. A-SPICE / ISO 26262 정합성 자체 점검

- A-SPICE (SYS.1/SYS.2/SWE.1 관점): 출처(source), 우선순위, 근거(rationale), 검증기준(verification criteria), 양방향 추적성, 검토 상태가 모든 요구사항에 존재하는가.
- ISO 26262 (안전 관련 요구사항 한정): ASIL 등급, 안전목표와의 연계, 요구사항 특성(모호하지 않음/이해가능/원자적/내적일관성/실현가능/검증가능/상위 레벨에서는 구현독립적) 충족 여부. 상세는 `references/iso26262.md` 참고.
- 두 표준 모두 본 스킬은 실무 보조 도구이며, 원문(ISO 26262 각 파트, Automotive SPICE PAM)을 대체하지 않는다는 점을 산출물에 명시한다.

## 출력물 구성

1. 요구사항 명세서 (템플릿 양식, 다이어그램 포함)
2. 추적성 매트릭스
3. 일관성 점검 결과
4. A-SPICE/ISO 26262 자체 점검 결과 (미충족 항목 강조)
