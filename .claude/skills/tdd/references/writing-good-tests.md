# 좋은 테스트 작성하기

> [obra/superpowers](https://github.com/obra/superpowers)의 `writing-good-tests.md`(MIT License)를 Python/`unittest` 예시로 각색.

**언제 이 문서를 읽는가:** 테스트를 작성/수정할 때, 목(mock)을 추가할 때, 테스트용 정리(cleanup)/헬퍼 메서드를 추가할 때.

## 개요

테스트는 특정한 "깨짐(break)"을 잡기 위해 존재한다. 여기서 다루는 모든 내용은 두 원칙으로 귀결된다.

```
1. 모든 테스트는 자신이 잡아내는 깨짐의 이름을 댈 수 있어야 한다
2. 모든 테스트는 실제 대상(real thing)을 실행해야 한다
```

엄격한 TDD는 이 둘을 자연스럽게 만족시킨다 — 먼저 작성되어 실제 코드에 대해 실패하는 것을 확인한 테스트는 이미 "실패할 수 있음"을 증명했고, 실제 의존성이 느리거나 외부 자원일 때만 목을 쓸 자격을 얻는다.

## 원칙 1: 깨짐의 이름을 대라

테스트 본문을 쓰기 전에 답한다: **어떤 프로덕션 코드 변경이 이 테스트를 실패시키는가 — 그리고 그 변경은 버그인가, 설계 결정인가?** 테스트는 잘못된 분기, 누락된 부작용, 잘못된 인자, 경계값, 깨진 계약을 잡아낼 때 존재 가치를 얻는다.

**기대값은 독립적으로 도출한다.** 리터럴 값과 직접 계산한 픽스처를 쓴다 — 표 기반 테스트에서 리터럴 `want` 값을 쓰는 방식이 선호된다. 테스트 대상 코드(또는 그 헬퍼)로 계산한 기대값은 그 코드가 무엇을 하든 항상 통과한다.

```python
# 잘못됨: 같은 빌더로 양쪽을 계산 — 항상 참
expected = buildSearchQuery({"tag": "urgent"})
self.assertEqual(buildSearchQuery({"tag": "urgent"}), expected)

# 올바름: 손으로 도출한 리터럴
self.assertEqual(buildSearchQuery({"tag": "urgent"}), 'tag:"urgent"')
```

**변경 감지기(change detector)를 만들지 않는다.** 의도적인 설계 결정만 실패시킬 수 있는 테스트 — 상수 값, 정확한 메시지 문구, 내부 구조 — 는 리팩토링 때마다 울리고 실제 버그에는 잠들어 있다. 결정 자체가 아니라 그 결정에 의존하는 동작을 테스트한다: `self.assertEqual(MAX_RETRIES, 5)`가 아니라 "실패한 호출이 5번 재시도되고 6번째 시도는 일어나지 않는다"를 검증한다.

**동작을, 텍스트가 아니라.** 스크립트나 설정 파일이 특정 줄을 포함하는지 검증하는 것은 소스가 소스라는 것만 증명한다. 통제된 입력으로 스크립트를 실행하고 출력/부작용/종료 코드를 단정한다.

**프레임워크가 아니라 당신의 코드.** 당신 코드가 경계에서 맺는 계약(등록하는 라우트, 실행하는 쿼리, 만들어내는 페이로드)을 테스트한다. 표준 라이브러리나 서드파티 프레임워크의 내부 동작은 그 관리자들의 테스트 몫이다. 생성자·getter·상수·단순 위임(forwarding)은 검증/정규화/기본값 설정/파생/강제/부작용을 수행할 때만 테스트할 가치가 있다 — 그렇지 않으면 그것에 의존하는 첫 번째 관찰 가능한 결과를 단정한다.

### 게이트 함수

```
테스트 본문을 쓰기 전에:
  이 테스트를 실패시킬 프로덕션 변경의 이름을 댄다.

  이름을 댈 수 없다면            → 관찰 가능한 동작 중심으로 재설계
  "소스 텍스트가 바뀌었다"라면    → 산출물을 실행하고 그 효과를 단정
  의도적 결정만 실패시킨다면      → 변경 감지기다; 그 결정에 의존하는 동작을 테스트

  기대값이 테스트 대상 코드 없이 도출되었는지 확인한다.
  테스트 대상의 로직/헬퍼를 재사용했다면:
    리터럴 또는 손으로 검증한 픽스처로 교체한다
```

## 원칙 2: 실제 대상을 실행하라

**목(mock)은 그 자체로 단정의 대상이 될 수 없다.** 목에 대한 단정은 목이 있으면 통과하고 없으면 실패한다 — 실제 컴포넌트에 대해서는 아무것도 말해주지 않는다. 실제 컴포넌트의 동작을 단정한다. 목이 검증 대상이라면 모킹을 풀거나 그 단정을 삭제한다.

```python
# 올바름: 실제 동작
self.assertTrue(response.headers.get("X-Request-Id"))

# 잘못됨: 목의 존재
self.assertTrue(mockLogger.info.called)
```

**적절한 수준에서 모킹한다.** 실제 메서드의 모든 부작용을 먼저 파악한 뒤, 느리거나 외부적인 연산만 교체하고 테스트가 의존하는 나머지는 실제로 남긴다. 확신이 없으면 실제 구현으로 먼저 테스트를 실행해 무엇이 실제로 필요한지 관찰한다.

**더블을 구체적으로 만든다.** 인자, 호출 횟수, 순서가 계약의 일부라면 그것을 단정한다 — 무엇이든 받아들이는 페이크는 아무것도 검증하지 않는다. 성공/오류/잘못된 형식 등 각 분기에 각자의 픽스처나 스파이를 둔다.

**목 데이터는 실제 구조를 완전히 반영한다.** 테스트가 읽는 필드만이 아니라 실제로 존재하는 모든 문서화된 필드를 모킹한다. 부분적인 목은 하위 코드가 누락된 필드를 읽을 때 조용히 실패한다 — 테스트는 통과하지만 통합은 깨진다.

**프로덕션 클래스에는 프로덕션 메서드만 둔다.** 테스트만 필요로 하는 정리(cleanup)를 프로덕션 클래스의 메서드로 만들지 않는다. 테스트 유틸리티에 둔다.

**복잡한 목보다 실제 컴포넌트를 선호한다.** 목 설정이 테스트 로직보다 커지거나, 목이 실제 컴포넌트의 메서드를 놓치거나, 목이 바뀔 때마다 테스트가 깨진다면 실제 컴포넌트를 쓰는 통합 테스트로 전환한다.

### 게이트 함수

```
목이나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부작용을 나열하고, 테스트가 의존하는 것은 실제로 남긴다;
  느리거나 외부적인 수준만 모킹한다.

  목의 응답이 실제 구조를 완전히 반영하는가.

  테스트만 호출하는 메서드는 프로덕션이 아니라 테스트 유틸리티에 둔다.

  목 자체를 단정하려는가?
    모킹을 풀거나 그 단정을 삭제한다.
```

## 테스트는 구현과 함께 완성된다

TDD 사이클(실패하는 테스트 → 최소 구현 → 리팩토링)이 "완료"의 정의다. 그 동작이 필요로 하는 테스트만 남긴다 — 자명한 코드와 사람이 읽는 설명문에는 테스트를 붙이지 않으며, 절차를 만족시키기 위해 쓴 테스트는 계속 유지보수 비용만 든다.

## Mutation Check (변이 점검)

작업을 끝내기 전에 프로덕션 코드를 머릿속으로 변형(mutate)해 본다. 현실적인 변형마다 최소 하나의 테스트가 실패해야 한다.

- 잘못된 상수/인자
- 잘못된 분기 처리
- 누락된 상태 변경/부작용
- 빈 값 또는 기본값 반환
- 0/빈 값/None/권한 없음/잘못된 형식 입력에 대한 검증 누락

어떤 변형도 잡아내지 못하는 테스트는 그 동작이 보호받지 못한다는 뜻이거나, 테스트가 항진명제(tautology)라는 뜻이다.

## 빠른 참조

| 할 때 | 해야 할 일 |
|---|---|
| 어떤 테스트든 작성할 때 | 그 테스트가 잡아내는 깨짐(버그, 결정 아님)의 이름을 대라 |
| 기대값을 만들 때 | 손으로 도출하라 — 테스트 대상 코드로 계산하지 말라 |
| 스크립트/문서를 테스트할 때 | 실행하거나 소비자의 동작으로 검증하라 — 텍스트를 grep하지 말라 |
| 의존성을 테스트하려 할 때 | 당신의 경계 계약을 테스트하라 — 그들의 문서화된 동작이 아니라 |
| 목에 단정하려 할 때 | 실제 컴포넌트를 테스트하거나, 모킹을 풀어라 |
| 메서드를 모킹하려 할 때 | 부작용을 먼저 파악하고, 느리거나 외부적인 수준만 모킹하라 |
| 목 응답을 만들 때 | 실제 구조를 완전히 반영하라 |
| 테스트 전용 정리(cleanup)가 필요할 때 | 테스트 유틸리티에 두라 |
| 목 설정이 비대해질 때 | 실제 컴포넌트를 쓰는 통합 테스트로 전환하라 |
| 테스트 파일을 끝낼 때 | Mutation Check를 실행하라 |

## 경고 신호

- 준비(setup)와 단정이 같은 객체를 공유해 항상 같음이 보장됨
- 예외/충돌/셀렉터 실패로만 테스트가 실패할 수 있음
- 의도적인 모든 변경에 실패하지만 실수로 인한 손상에는 실패하지 않음
- 기대값이 루프/빌더/헬퍼 뒤에 숨겨져 있음
- 소스 텍스트를 grep하거나, 제거된 심볼이 계속 없는지만 확인함
- 프레임워크만 남아도 여전히 통과할 테스트
- 부작용/결과를 확인하지 않고 커버리지만을 위해 존재함
- `*-mock` 같은 테스트 ID에 대한 단정, 또는 목을 제거하면 실패하는 단정
- 어떤 메서드가 테스트 파일에서만 호출됨
- 목 설정이 테스트의 절반 이상을 차지하거나 왜 필요한지 설명할 수 없음
- "혹시 몰라서" 모킹함
