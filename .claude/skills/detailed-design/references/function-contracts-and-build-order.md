# 함수 계약 명세 및 단위 구현·통합 순서

## 1. 함수 계약 원칙 (필수)

- **모듈/함수 간 통신은 반드시 명시된 함수 계약(공개 API)으로만 이루어진다.** 다른 모듈의 내부 정적 변수, 구조체 필드, 전역 상태에 대한 직접 접근을 금지한다.
- 각 모듈은 **공개 인터페이스(헤더/공개 API)** 와 **내부 구현(비공개)**을 구분한다. 공개 인터페이스에 포함되지 않은 함수/데이터는 외부에서 참조할 수 없다.
- 함수 계약은 Design by Contract 형태로 정의한다: 호출 전 조건, 호출 후 보장, 실패 시 계약을 명확히 한다.

### 함수 계약 테이블 (템플릿 5장에 사용)

| 필드 | 설명 |
|---|---|
| 함수 ID | 고유 식별자 (예: `FN-MOD03-012`) |
| 소속 모듈/구현 단위 | 템플릿 2장의 모듈 ID |
| 시그니처 | 함수명, 파라미터 타입, 반환 타입 |
| 사전조건 | 호출 전 성립해야 하는 조건(입력 범위, 상태) |
| 사후조건 | 호출 후 보장되는 결과 |
| 부작용(Side effect) | 상태 변경, I/O, 로깅 등 |
| 오류/예외 계약 | 실패 시 반환값/예외/오류 코드와 호출자의 기대 동작 |
| 시간 제약 | 최대 실행시간, 호출 주기, 재진입성 여부 |
| 할당 요구사항/아키텍처 인터페이스 ID | 이 함수가 구현하는 SW 요구사항 및 상위 아키텍처 인터페이스 |

## 2. 정적 호출관계 검증 (템플릿 3장과 연계)

1. 모듈/함수 호출 그래프를 Mermaid로 작성한다.
2. 순환 호출(cyclic call dependency)이 있는지 확인한다. 발견되면 공통 기능을 별도 모듈로 추출하거나 콜백/인터페이스로 역전하여 제거한다.
3. 호출 방향이 상위(정책) → 하위(구체 구현) 인터페이스를 향하는지, 반대로 하위가 상위 구체 함수를 직접 호출하지 않는지 확인한다.

## 3. 단위 구현·통합 순서 정의 (필수, 템플릿 12장과 연계)

상위 아키텍처의 통합 순서(컴포넌트 단위)를 그대로 이어받아, **모듈/함수 단위의 구현(construction) 및 단위 통합 순서**를 정의한다.

### 순서 테이블

| 순서 | 구현 대상(모듈/함수) | 선행조건(먼저 구현/검증되어야 하는 단위) | 필요 스텁/드라이버 | 단위시험 관점(검증 목적) | 순서 근거 |
|---|---|---|---|---|---|
| 1 | ... | 없음(최하위 유틸리티) | ... | ... | ... |
| 2 | ... | 1 | ... | ... | ... |

- 순서 근거에는 "왜 이 단위가 이 시점에 구현/통합되어야 하는가"(호출 의존성, 위험도, 재사용성, 테스트 용이성)를 반드시 기술한다.
- 이 순서는 상위 아키텍처 통합 전략(예: 상향식)과 모순되지 않아야 하며, 모순 시 아키텍처 문서와의 불일치로 보고한다.
- 식별자는 `TPL-SWE4-001/002`(단위시험 명세서/결과서 템플릿)에서 재사용할 수 있도록 일관되게 명명한다(추적성 유지).
