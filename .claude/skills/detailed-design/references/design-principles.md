# 상세설계 원칙: 단위 수준 응집도/결합도, SOLID, ISO 26262-6 구현 원칙

상위 아키텍처 설계(`architecture-design` 스킬)에서 정의된 컴포넌트/인터페이스 구조는 이 단계에서 변경하지 않는다. 상세설계는 **아키텍처가 정한 경계 안에서** 모듈·함수·클래스·자료구조 단위로 내려간다.

## 1. 단위 수준 응집도(Cohesion)

모듈 분해(템플릿 2장) 및 함수 계약(5장) 작성 시 각 구현 단위(모듈/클래스/함수)에 응집도 유형을 판정한다. 판정 기준은 `architecture-design` 스킬의 응집도 순위표와 동일하며, **함수/클래스 수준에서도 기능적 응집(하나의 함수는 하나의 일을 한다)**을 목표로 한다. 논리적/우연적 응집(예: "여러 무관한 유틸리티를 모아 놓은 함수")은 재설계한다.

## 2. 단위 수준 결합도(Coupling)

호출관계(3장)와 공통 자료형(4장) 작성 시 결합도 유형을 판정한다. **데이터 결합(필요한 값만 매개변수로 전달)을 목표**로 하며 다음을 금지 사항으로 취급한다.

- 전역 변수/공유 상태를 통한 모듈 간 암묵적 통신 (공통 결합)
- 다른 모듈의 내부 자료구조 필드에 직접 접근하거나 수정 (내용 결합)
- "동작 모드" 플래그를 넘겨 호출 대상의 분기 로직을 원격 제어하는 방식 (제어 결합) — 불가피한 경우 근거를 명시

모든 모듈 간 상호작용은 5장에서 정의한 **함수 계약(인터페이스)** 을 통해서만 이루어진다. 이는 아키텍처 단계의 "컴포넌트는 인터페이스로만 통신한다" 원칙을 함수/모듈 단위로 그대로 계승한 것이다.

## 3. SOLID 원칙 — 단위 수준 적용

| 원칙 | 상세설계에서의 점검 질문 | 위반 시 조치 |
|---|---|---|
| SRP | 이 함수/클래스가 변경되어야 할 이유가 하나뿐인가? 함수 이름에 "and"가 필요한가? | 함수를 분리 |
| OCP | 정책/규칙(7장 정책 의사결정표)이 변경될 때 기존 함수 본문을 고치지 않고 테이블/전략 객체 교체로 대응 가능한가? | 조건 분기를 데이터 기반 테이블이나 전략(strategy) 함수 포인터/콜백으로 재설계 |
| LSP | 동일 계약(5장)을 구현하는 함수를 교체해도 호출자의 사전/사후조건, 오류 계약이 깨지지 않는가? | 계약을 명확히 하거나 별도 계약으로 분리 |
| ISP | 헤더/모듈이 호출자가 쓰지 않는 함수까지 강제로 노출하는가? | 헤더/공개 API를 사용자별로 분리 |
| DIP | 상위 정책 로직이 특정 HW/드라이버/외부 라이브러리 구체 구현을 직접 호출하는가, 아니면 아키텍처가 정의한 인터페이스를 통하는가? | 콜백/함수 포인터/추상 인터페이스로 역전 |

각 핵심 모듈/함수에 대해 Pass/Fail과 근거를 남긴다. Fail 항목은 재설계 없이 통과시키지 않는다.

## 4. ISO 26262-6 상세설계 및 구현 원칙

ISO 26262 Part 6에서 소프트웨어 단위 설계 및 구현에 요구하는 원칙을 코딩 및 검증 규칙(템플릿 11장)과 핵심 알고리즘(6장) 작성 시 반영한다. 대표 항목:

- **단순성/제한된 복잡도**: 함수 크기, 순환복잡도(cyclomatic complexity) 상한을 프로젝트 기준으로 정의하고 초과 시 분해한다.
- **하나의 진입점/하나의 종료점**: 함수는 원칙적으로 단일 entry/단일 exit 구조를 지향한다(과도한 조기 return, goto 사용 제한 — ASIL 등급에 따라 구체 규칙 결정).
- **강한 타입 지정 및 초기화**: 변수는 사용 전 명시적으로 초기화하고, 암묵적 타입 변환을 피한다.
- **포인터/동적 메모리/재귀/인터럽트 사용 제한**: 안전요구사항에서 파생된 ASIL 등급에 따라 이 기법들의 사용을 제한하거나 금지하고, 사용하는 경우 근거와 안전성 논거를 남긴다.
- **방어적 프로그래밍**: 입력 유효성 검증, 경계값 처리, 실패 시 안전한 기본 동작(10장 오류와 방어 동작)을 모든 공개 함수 계약에 포함한다.
- **코딩 표준 준수**: 프로젝트에서 채택한 코딩 표준(예: MISRA C/C++ 계열 등 실제 프로젝트 표준)과 정적분석 도구 적용 여부를 11장에 기록한다. 표준 명칭은 실제 프로젝트에서 사용하는 것을 확인 후 기입하며, 임의로 가정하지 않는다.

**주의**: 본 참고자료는 실무 적용을 돕기 위한 요약이며, ASIL 등급별 정확한 권고 표는 반드시 ISO 26262-6 원문과 대조해 확정한다. 이 스킬의 산출물은 원문을 대체하지 않는다.

## 5. 설계 대안 검토 (해당하는 경우에만)

모듈 분해 자체는 상위 아키텍처에서 이미 결정되었으므로 다시 후보를 제시하지 않는다. 다만 **알고리즘 선택이나 자료구조 선택이 성능/메모리/안전성에 의미 있는 영향을 주는 단위**(예: 탐색/정렬 알고리즘, 캐시 전략, 동시성 제어 방식)에 대해서는 2~3개 대안을 비교표로 제시하고 사용자가 선택하게 한다. 트리비얼한 단위(단순 getter/setter, 단순 변환 함수 등)에는 이 절차를 적용하지 않는다.
