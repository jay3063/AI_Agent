# 상세설계 스킬

## 0. 템플릿 및 상위 아키텍처 확인 (최우선)

- `references/template.md`를 연다. 이 파일은 실제 공식 템플릿
  `WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SWE3-001_SW 상세설계서 템플릿.docx`
  의 목차/작성 안내를 그대로 반영한 작업용 사본이며 **PLACEHOLDER가 아니다.**
- 산출물의 섹션 번호와 제목은 이 템플릿 순서를 **그대로** 따른다.
- 다이어그램은 `TPL-SWE3-002_상세설계 UML 및 호출관계 템플릿.drawio`의 표기 규칙(구현 단위와 책임, 함수/클래스 호출, 입출력 자료형, 설계·시험 추적 ID)을 따르되, 산출물 본문에는 Mermaid 코드 블록으로 동일 내용을 표현한다.
- **상세설계는 아키텍처 설계의 하위 단계다.** 대상 컴포넌트의 아키텍처 설계서(가능하면 `architecture-design` 스킬 산출물)를 먼저 확인하여, 컴포넌트 경계·인터페이스·통합 순서를 재작성하지 않고 그 안에서 모듈/함수 단위로 세분화한다. 아키텍처 산출물이 없거나 모순되면 임의로 진행하지 말고 사용자에게 알린다.

## 1. 컨텍스트 파악

- 상세설계 대상 아키텍처 요소(컴포넌트)의 책임, 제공/요구 인터페이스, 할당 요구사항을 실제 문서에서 확인한다.
- 안전 관련 여부(ASIL 등급), 실시간성 요구, 실제 채택된 코딩 표준/정적분석 도구를 확인한다(가정하지 않는다. 없으면 "미확인"으로 기록).

## 2. 모듈 분해 (템플릿 2장)

1. 아키텍처 요소를 구현 단위(모듈/클래스/파일)로 분해한다. 각 단위에 ID, 책임(단일 문장), 소스 위치를 부여한다.
2. 각 단위의 **응집도 유형**(기능적 응집 목표)을 판정하고 근거를 기록한다. `references/design-principles.md` 1절 기준.

## 3. 상세 호출관계 및 정적 검증 (템플릿 3장)

`references/function-contracts-and-build-order.md` 2절을 따른다.

1. 함수/클래스 호출 그래프를 Mermaid로 작성한다.
2. 순환 호출 의존이 없는지 검증한다. 있으면 콜백/인터페이스 역전 또는 공통 모듈 추출로 제거한다.
3. 호출 방향이 상위 정책 → 하위 구현 인터페이스를 향하는지 확인한다(DIP).

## 4. 공통 자료형 (템플릿 4장)

공통 데이터 구조, 열거형, 단위, 범위, 불변조건, 직렬화 규칙을 정의한다. 여러 모듈이 동일 자료형을 각자 다르게 정의하지 않도록 단일 정의 위치를 명시한다.

## 5. 핵심 함수 계약 — 모듈 간 통신은 계약으로만 (필수, 템플릿 5장)

`references/function-contracts-and-build-order.md` 1절을 따른다.

1. **반드시** 모듈/함수 간 상호작용에 대해 공개 함수 계약(시그니처, 사전/사후조건, 부작용, 오류 계약, 시간 제약, 할당 요구사항/아키텍처 인터페이스 ID)을 정의한다.
2. 다른 모듈의 내부 정적 변수·구조체 필드·전역 상태에 대한 직접 접근은 금지한다. 공개 인터페이스에 없는 함수/데이터는 외부에서 참조할 수 없다.
3. 각 모듈 간 관계에 **결합도 유형**(데이터 결합 목표)을 판정한다. 공통/내용/제어 결합이 발견되면 재설계한다(`references/design-principles.md` 2절).
4. 핵심 모듈/함수에 **SOLID 5원칙**(SRP/OCP/LSP/ISP/DIP)을 Pass/Fail로 판정한다(`references/design-principles.md` 3절). Fail은 재설계한다.

## 6. 핵심 알고리즘 및 설계 대안 (템플릿 6장)

1. 처리 순서, 판단 조건, 경계값, 계산 근거를 의사코드 또는 흐름도(Mermaid `flowchart`)로 작성한다.
2. 알고리즘/자료구조 선택이 성능·메모리·안전성에 의미 있는 영향을 주는 단위에 한해, 2~3개 대안을 비교표로 제시하고 `AskUserQuestion`으로 사용자가 선택하게 한다(`references/design-principles.md` 5절). 트리비얼한 단위에는 적용하지 않는다.

## 7. 정책 의사결정표 / 상태전이 상세 / Web·API 상세 (템플릿 7~9장)

- 정책 의사결정표: 입력 조건 조합, 우선순위, 기대 동작, 충돌 해결 규칙을 표로 작성한다.
- 상태전이 상세: 상태 저장 위치, 전이 함수, 이벤트, 가드, 타이머, 초기화 동작을 정의한다(상위 아키텍처의 상태전이 개요와 모순되지 않아야 함).
- Web/API 상세: 해당하는 경우에만 엔드포인트, 요청/응답 구조, 검증, 오류 코드, 세션/보안 경계를 정의한다.

## 8. 오류와 방어 동작 (템플릿 10장)

유효하지 않은 입력, 예외, 자원 실패에 대한 검출·처리·기록·복구를 정의한다. 안전 관련 단위는 ASIL과 연계하여 실패 시 안전한 기본 동작을 명시한다.

## 9. 코딩 및 검증 규칙 (템플릿 11장)

`references/design-principles.md` 4절(ISO 26262-6 상세설계·구현 원칙)을 반영하여 코딩 표준, 정적분석, 단위검증, 커버리지, 리뷰 기준을 기록한다. 실제 프로젝트가 채택한 표준/도구를 확인 후 기입하며, 임의로 가정하지 않는다.

## 10. 단위 구현·통합 순서 (필수, 템플릿 12장과 연계)

`references/function-contracts-and-build-order.md` 3절을 따른다.

1. 모듈/함수 단위의 구현(construction) 및 단위 통합 순서 테이블(순서, 대상, 선행조건, 필요 스텁/드라이버, 검증 목적, 순서 근거)을 작성한다. **근거 없는 순서 배정은 금지한다.**
2. 이 순서가 상위 아키텍처 통합 전략과 모순되지 않는지 확인한다. 모순 시 불일치로 보고하고 임의로 조정하지 않는다.

## 11. 단위/요구사항 할당, 구현 경계, 추적성 (템플릿 12~14장)

1. 구현 단위를 아키텍처 요소, SW 요구사항, 단위시험에 연결한다. 할당되지 않은 요구사항, 근거 없는 단위를 모두 보고한다.
2. 구현 경계(생성 코드, 외부 라이브러리/FOSS, 플랫폼 종속부, 구현 제외 범위)를 명시한다.
3. 아키텍처 ↔ 상세설계 ↔ 소스 파일/함수 ↔ 단위시험 간 양방향 추적성을 확립한다.

## 12. A-SPICE / ISO 26262 자체 점검 (필수)

`references/aspice-iso26262-checklist.md`를 따라 A-SPICE SWE.3 BP1~BP6과 ISO 26262-6 상세설계·구현 관련 항목을 자체 점검하고, 문서 최종 섹션에 별도로 제시한다.

## 출력물 구성 (TPL-SWE3-001 순서 준수)

1. 문서 통제(작성/검토/승인 상태, 변경 이력)
2. 목적 및 적용범위 ~ 적용 경계
3. 모듈 분해 + 응집도 자체 점검
4. 상세 호출관계(순환 없음 확인)
5. 공통 자료형
6. 핵심 함수 계약 + 결합도/SOLID 자체 점검표
7. 핵심 알고리즘(+ 설계 대안 검토, 해당 시)
8. 정책 의사결정표
9. 상태전이 상세
10. Web 및 API 상세 (해당 시)
11. 오류와 방어 동작
12. 코딩 및 검증 규칙
13. 단위 구현·통합 순서 테이블
14. 단위와 요구사항 할당
15. 구현 경계
16. 추적성
17. 참고자료
18. A-SPICE SWE.3 / ISO 26262-6 자체 점검 결과

## 원칙

- 상위 아키텍처가 정한 컴포넌트 경계·인터페이스·통합 순서를 이 단계에서 임의로 재정의하지 않는다.
- 모듈 간 통신은 함수 계약으로만 이루어져야 하며, 응집도/결합도/SOLID 판정과 단위 구현·통합 순서는 선택 사항이 아니라 필수 항목이다.
- 본 스킬은 실무 보조 도구이며 Automotive SPICE PAM, ISO 26262 원문을 대체하지 않는다는 점을 산출물에 명시한다.
- 산출물은 사용자가 사용한 언어(기본: 한국어)로 작성한다.
