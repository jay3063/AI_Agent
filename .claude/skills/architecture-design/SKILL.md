# 아키텍처 설계 스킬

## 0. 템플릿 확인 (최우선)

- `references/template.md`를 연다. 이 파일은 실제 공식 템플릿
  `WP_Templates/Engineering/SoftwareArchitecturalDesign/TPL-SWE2-001_SW 아키텍처 설계서 템플릿.docx`
  의 목차/작성 안내를 그대로 반영한 작업용 사본이며 **PLACEHOLDER가 아니다.**
- 산출물의 섹션 번호와 제목은 이 템플릿 순서를 **그대로** 따른다. 임의로 섹션을 생략·재배열하지 않는다.
- 다이어그램은 `TPL-SWE2-002_SW 아키텍처 UML 템플릿.drawio`의 표기 규칙(요소 ID+명칭, 제공/요구 인터페이스, 의존 방향, 요구사항 할당 ID)을 따르되, 산출물 본문에는 Mermaid 코드 블록으로 동일 내용을 표현한다.
- 만약 위 경로의 템플릿 파일이 실제로 존재하지 않거나 내용이 다르면, 임의로 진행하지 말고 사용자에게 알린 뒤 `references/template.md`를 최신 상태로 갱신한다.

## 1. 컨텍스트 파악

작업을 시작하기 전에 다음을 확인한다(대상 문서/요구사항이 있으면 실제로 열어 확인한다).

- 대상 시스템/소프트웨어의 범위, 안전 관련 여부(ASIL 등급), 실시간성 요구
- 입력 요구사항 명세(가능하면 `requirements-analysis` 스킬 산출물 또는 SW 요구사항 문서)의 존재 여부와 위치
- 변경이 자주 발생할 것으로 예상되는 지점(신규 기능 추가, HW/벤더 교체, 변형 제품 등)

## 2. 아키텍처 후보 제안 및 선정 (필수 — 상세 설계 이전 단계)

**반드시** 상세 설계(템플릿 3장 이후)에 들어가기 전에 이 단계를 먼저 수행한다.

1. `references/architecture-patterns.md`의 비교표를 참고하여, 1절에서 파악한 컨텍스트에 맞는 **2~4개의 후보 아키텍처 구조**를 선별한다(전체 목록을 그대로 나열하지 않는다).
2. 각 후보에 대해 구조 개요(Mermaid), 응집도/결합도 특성, 변경 유연성, SOLID 부합도, ISO 26262-6 설계 원칙 부합도, 리스크/트레이드오프를 표로 제시한다.
3. 사용자에게 후보를 제시하고 하나를 선정(또는 조건부 조합을 지시)하게 한다 — 가능하면 `AskUserQuestion` 도구를 사용한다.
4. **사용자가 후보를 선정하기 전에는 3장 이후 상세 설계로 진행하지 않는다.**
5. 선정 결과를 ADR(Architecture Decision Record)로 기록한다: 결정 배경, 검토한 대안, 선택 이유, 감수하는 트레이드오프, 결정자·일자. 이 ADR은 산출물의 부속 자료(15장 참고자료 또는 별도 섹션)로 포함한다.

## 3. 설계 원칙 적용 — 응집도/낮은 결합도/SOLID (필수)

`references/design-principles.md`를 따른다.

1. 모든 컴포넌트에 대해 **응집도 유형**(기능적 응집을 목표)을 판정하고 근거를 기록한다. 논리적/우연적 응집으로 판정되면 컴포넌트를 재설계한다.
2. 모든 컴포넌트 관계에 대해 **결합도 유형**(데이터 결합을 목표)을 판정한다. 공통 결합·내용 결합은 금지 사항으로 처리하고 재설계 없이 통과시키지 않는다.
3. 컴포넌트별로 **SOLID 5원칙 체크리스트**(SRP/OCP/LSP/ISP/DIP)를 Pass/Fail로 판정하고 근거를 남긴다. Fail 항목은 재설계한다.
4. ISO 26262-6 아키텍처 설계 원칙(계층 구조, 크기/복잡도 제한, 높은 응집도, 낮은 결합도, 명확한 인터페이스, 오류 검출/처리, ASIL별 설계 기법 제약)과의 정합성을 템플릿 2장(아키텍처 설계 원칙)에 명시적으로 서술한다.

## 4. 논리 아키텍처 및 컴포넌트 책임 (템플릿 3~4장)

1. 선정된 아키텍처 구조에 따라 요소/계층/관계를 정의한다(요소 ID, 명칭, 목적, 제공 기능, 소유 책임).
2. 각 컴포넌트의 책임을 **단일 문장**으로 기술한다(SRP 위반 방지). 입력/출력/상태/오류 처리/할당 요구사항을 함께 명시한다.
3. 어떤 컴포넌트도 다른 컴포넌트의 내부 데이터 구조나 상태를 직접 참조하지 않도록 설계한다 — 상호작용은 5절/6절의 인터페이스로만 이루어진다.

## 5. 인터페이스 정의 — 컴포넌트 간 통신은 인터페이스로만 (필수)

`references/interface-and-integration.md`의 1절을 따른다.

1. **반드시** 모든 컴포넌트 간 상호작용에 대해 인터페이스(제공/요구 포트)를 정의한다. 정의되지 않은 통신 경로(전역 변수 공유, 내부 필드 직접 접근 등)는 금지한다.
2. 인터페이스 명세 테이블(ID, 구분, 제공자, 사용자, 연산/시그니처, 데이터 계약, 사전/사후조건, 시간 제약, 오류 계약, 재진입성, 버전, 할당 요구사항 ID)을 작성한다.
3. 내부 인터페이스(6.1)와 외부 인터페이스(6.2)를 구분하여 작성한다.
4. 정적 의존성 그래프를 작성하고 순환 의존이 없는지 검증한다. 순환이 발견되면 인터페이스를 추출/역전하여 제거한다(방치 금지).

## 6. 동적 동작 / 상태 전이 / 오류 격리 (템플릿 7~9장)

1. 주요 시나리오의 호출 순서와 데이터 흐름을 시퀀스 관점(Mermaid `sequenceDiagram`)으로 기술한다.
2. 상태를 갖는 컴포넌트는 상태 전이(Mermaid `stateDiagram-v2`)를 정의한다(진입/종료 조건, 전이 이벤트, 가드, 금지 전이 포함).
3. 오류 감지 위치, 전파 차단 경계(오류 격리), 안전 상태, 복구 절차, 진단 정보 책임을 정의하고 ASIL과 연계한다.

## 7. 품질속성 분석 (템플릿 10장)

주요 품질속성(성능, 신뢰성, 유지보수성, 이식성 등)별로 대표 시나리오를 정의하고, 선정된 아키텍처가 해당 시나리오에 어떻게 대응하는지 분석한다. 정성적 서술만 있는 항목은 정량적 기준(수치/조건)을 추가한다.

## 8. 통합 순서 정의 (필수, 템플릿 11장)

`references/interface-and-integration.md`의 3절을 따른다.

1. 통합 전략(상향식/하향식/위험 기반/빅뱅 중 선택, 빅뱅은 근거 필수)을 정하고 이유를 기술한다.
2. 통합 순서 테이블(순서, 통합 대상, 선행조건, 필요 스텁/드라이버, 검증 목적, 순서 근거)을 작성한다. **순서 근거 없는 배정은 금지한다.**
3. 통합 대상/식별자는 `TPL-SWE5-001/002/003`(통합전략·통합시험 명세/케이스/결과 템플릿)에서 재사용 가능하도록 일관되게 명명한다.

## 9. 요구사항 할당 및 추적성 (템플릿 12, 14장)

1. SW 요구사항을 아키텍처 요소/인터페이스에 할당한다. 할당되지 않은 요구사항, 근거 없는 컴포넌트(요구사항과 연결되지 않는 컴포넌트)를 모두 보고한다.
2. 요구사항 ↔ 아키텍처 요소 ↔ 인터페이스 ↔ (가능하면) 상세설계/통합시험 간 양방향 추적성을 확립한다.

## 10. 자원 및 배포 경계 (템플릿 13장)

실행 노드, 프로세스, 메모리/CPU/저장소 예산, 배포 제약을 정의한다.

## 11. A-SPICE / ISO 26262 자체 점검 (필수)

`references/aspice-iso26262-checklist.md`를 따라 A-SPICE SWE.2 BP1~BP9와 ISO 26262-6 관련 항목을 자체 점검하고, 문서 최종 섹션에 별도로 제시한다. 미충족 항목은 재설계/보완 권고와 함께 명시한다.

## 출력물 구성 (TPL-SWE2-001 순서 준수)

1. 문서 통제(작성/검토/승인 상태, 변경 이력)
2. 목적 및 적용범위 ~ 적용 경계
3. 아키텍처 설계 원칙 (응집도/결합도/SOLID/ISO 26262-6 정합성 포함)
4. 논리 아키텍처(요소/관계)
5. 컴포넌트 책임 + SOLID/응집도 자체 점검표
6. 정적 의존성(순환 없음 확인)
7. 인터페이스 명세(내부/외부)
8. 동적 동작 / 상태 전이
9. 오류 격리와 안전 동작
10. 품질속성 분석
11. 통합 전략 및 통합 순서 테이블
12. 요구사항 할당
13. 자원 및 배포 경계
14. 추적성
15. 참고자료 + 아키텍처 후보 제안/선정 ADR
16. A-SPICE SWE.2 / ISO 26262-6 자체 점검 결과

## 원칙

- 본 스킬은 실무 보조 도구이며 Automotive SPICE PAM, ISO 26262 원문을 대체하지 않는다는 점을 산출물에 명시한다.
- 사용자가 아키텍처 후보를 선정하기 전에는 상세 설계를 임의로 확정하지 않는다.
- 산출물은 사용자가 사용한 언어(기본: 한국어)로 작성한다.

## 경계 (이 스킬이 다루지 않는 것)

- **모듈/함수 단위 상세설계는 다루지 않는다.** 컴포넌트 내부를 모듈/함수로 세분화하는 것은 `detailed-design`(`detailed-designer`)의 몫이며, 이 스킬이 정한 컴포넌트 경계·인터페이스·통합 순서를 그 단계에서 재정의하지 않는다.
- **통합시험 케이스는 작성하지 않는다.** 이 스킬이 정의하는 인터페이스 명세와 통합 순서는 통합시험의 테스트 베이시스가 되지만, 실제 시험 케이스/실행/커버리지 측정은 `integration-testing`(`integration-tester`)의 몫이다.
