# 아키텍처 후보 패턴 및 제안 방법

## 원칙

- 아키텍처 상세 설계(템플릿 섹션 3 이후)에 착수하기 **전에** 반드시 2~4개의 후보 아키텍처 구조를 제안하고, 사용자가 하나를 선정(또는 혼합안을 지시)하게 한다.
- 후보는 프로젝트 컨텍스트(임베디드/자동차 SW 여부, 실시간성 요구, 변경 빈도가 예상되는 지점, 팀 구조)에 맞게 아래 목록에서 **선별**한다. 목록 전체를 기계적으로 나열하지 않는다.
- 각 후보는 응집도/결합도 특성, 변경 유연성, SOLID 적합성, ISO 26262-6 설계 원칙과의 정합성, 리스크를 함께 제시해야 사용자가 실질적으로 비교/선택할 수 있다.

## 후보 패턴 비교표 (선별용 참고자료)

| 패턴 | 핵심 아이디어 | 응집도/결합도 특성 | 변경 유연성 | SOLID 적합성 | 적합 상황 | 주의 리스크 |
|---|---|---|---|---|---|---|
| 계층형(Layered) | 응용/서비스/기본SW/HAL 등 수직 계층으로 분해, 상위→하위 단방향 의존 | 계층 내 기능적 응집 유도, 계층 간 데이터 결합 위주로 낮게 유지 가능 | 계층 경계가 명확하면 하위 교체 용이, 계층이 너무 굵으면 경직 | DIP 위반 위험(상위가 하위 구현에 직접 의존) → 계층 간 인터페이스 강제 필요 | ISO 26262-6의 계층 구조(hierarchical structure) 원칙과 직접 부합, AUTOSAR 유사 스택 | 계층을 우회하는 지름길 호출(layer skipping) 발생 시 결합도 급증 |
| 컴포넌트 기반(Component-Based, Port 지향) | 컴포넌트가 Provided/Required 포트(인터페이스)만 노출, AUTOSAR SWC 유사 | 컴포넌트별 기능적 응집 강제, 포트 계약으로 데이터 결합 유지 | 포트 계약만 유지하면 구현 교체가 매우 쉬움 | ISP(포트별 최소 인터페이스), DIP(포트=추상화) 자연스럽게 만족 | 요구사항 할당·추적성이 중요한 자동차 SW, 재사용 부품이 많은 경우 | 포트 정의가 과다하게 세분화되면 통합 복잡도 증가 |
| 헥사고날/포트-어댑터(Hexagonal, Ports & Adapters) | 도메인 로직을 중심에 두고 HW/외부 I/O는 어댑터로 격리 | 도메인 코어는 기능적 응집, 외부 의존은 어댑터에 고립되어 결합 최소화 | HW/툴체인/프로토콜 교체가 도메인 로직에 영향 없음 → 변경 유연성 최고 수준 | DIP를 구조적으로 강제(코어가 포트 인터페이스에만 의존) | 테스트 용이성이 중요하거나 HW 벤더 변경 가능성이 있는 프로젝트 | 임베디드 자원 제약 환경에서 어댑터 계층 오버헤드 관리 필요 |
| 마이크로커널/플러그인(Microkernel) | 최소 코어 + 교체 가능한 플러그인/확장 모듈 | 코어는 높은 응집, 플러그인 간 결합은 코어 인터페이스로만 발생 | 신규 기능을 플러그인으로 추가(OCP) — 기존 코어 미변경 | OCP를 구조적으로 지원 | 변형(Variant)이 많은 제품 라인, 기능 옵션이 잦은 경우 | 플러그인 간 숨은 순서 의존(로드 순서)이 생기면 결합도 은폐 위험 |
| 이벤트 기반/발행-구독(Event-Driven, Pub-Sub) | 컴포넌트가 이벤트 버스를 통해 비동기로 통신 | 발행자-구독자 간 직접 의존 제거 → 결합도 매우 낮음 | 신규 구독자 추가가 기존 컴포넌트에 영향 없음 | OCP에 강점, 단 인터페이스(이벤트 스키마) 계약 관리 필요 | 다수 소비자가 동일 데이터를 사용하는 경우, 느슨한 결합이 우선인 경우 | 비결정적 타이밍 → 안전 필수 실시간 제어 루프에는 부적합할 수 있음(ISO 26262 타이밍 분석 필요) |
| 파이프-필터(Pipe-Filter) | 데이터가 필터 체인을 순차 통과 | 각 필터는 단일 변환 책임(기능적 응집) | 필터 추가/교체 용이 | SRP에 강점 | 신호처리/센서퓨전 등 데이터 변환 체인 | 제어 흐름(상태/우선순위)이 복잡한 경우 표현력 부족 |

## 제안 절차

1. 프로젝트 컨텍스트(안전 등급, 실시간성, 변경 예상 지점, 재사용 요구)를 먼저 확인한다.
2. 위 표에서 컨텍스트에 맞는 2~4개 후보를 선별한다. 필요하면 두 패턴을 조합한 하이브리드 후보(예: "계층형 + 헥사고날 코어")도 후보에 포함할 수 있다.
3. 후보별로 다음을 표로 제시한다: 구조 개요(간단한 Mermaid 다이어그램), 응집도/결합도 평가, 변경 유연성 평가, SOLID 부합도, ISO 26262-6 원칙 부합도, 리스크/트레이드오프.
4. `AskUserQuestion` 도구로 후보를 제시하고 사용자가 하나를 선정(또는 조건부 조합을 지시)하게 한다. **사용자 선정 전에는 섹션 3 이후 상세 설계로 진행하지 않는다.**
5. 선정 결과와 근거를 ADR(Architecture Decision Record) 형식으로 기록한다: 결정 배경, 검토한 대안, 선택 이유, 결과로 받아들이는 트레이드오프, 결정자.
