# A-SPICE SWE.2 / ISO 26262-6 자체 점검 체크리스트

본 스킬은 실무 보조 도구이며, **Automotive SPICE PAM 원문과 ISO 26262 Part 6 원문을 대체하지 않는다.** 공식 심사·인증·계약상 근거가 필요한 경우 원문과 대조해야 한다는 점을 산출물에 명시한다.

## A-SPICE 4.1 SWE.2 (Software Architectural Design) Base Practice 자체 점검

| BP | 점검 항목 | 확인 위치(템플릿 섹션) |
|---|---|---|
| BP1 | 소프트웨어 아키텍처를 개발했는가(요소, 계층, 관계 식별) | 3. 논리 아키텍처 |
| BP2 | 아키텍처 요소 간 외부/내부 인터페이스를 식별했는가 | 6. 인터페이스 명세 |
| BP3 | 아키텍처의 동적 동작(자원 사용, 시간 동작 포함)을 기술했는가 | 7. 동적 동작, 8. 상태 전이, 13. 자원 및 배포 경계 |
| BP4 | 아키텍처가 자원 사용(메모리/CPU 등) 요구사항과 일치하는지 평가했는가 | 10. 품질속성 분석, 13. 자원 및 배포 경계 |
| BP5 | 대안 소프트웨어 아키텍처를 평가하고 선택 기준을 정의했는가 | 후보 제안/선정 ADR (`references/architecture-patterns.md` 절차) |
| BP6 | 소프트웨어 요소 통합 순서를 정의했는가 | 11. 통합 전략 |
| BP7 | 아키텍처가 SW 요구사항과 일관되는지 평가했는가(요구사항 할당) | 12. 요구사항 할당 |
| BP8 | 양방향 추적성(요구사항 ↔ 아키텍처 요소)을 확립했는가 | 14. 추적성 |
| BP9 | 이해관계자와 아키텍처를 합의(리뷰/승인)했는가 | 문서 통제(작성/검토/승인 상태) |

각 BP에 대해 "충족/부분충족/미충족"과 근거(문서 섹션·문구)를 명시한다. 근거 없는 판정은 금지한다.

## ISO 26262-6 (소프트웨어 개발) 아키텍처 설계 관련 자체 점검

| 항목 | 점검 질문 |
|---|---|
| 설계 원칙 반영 | 계층 구조, 컴포넌트/인터페이스 크기 제한, 높은 응집도, 낮은 결합도가 아키텍처 설계 원칙(섹션 2)에 명시적으로 기술되었는가 |
| 인터페이스 정의 | 모든 아키텍처 요소 간 상호작용이 명확히 정의된 인터페이스를 통해서만 이루어지는가(6장) |
| 오류 검출/처리 | 오류 감지, 전파 차단, 안전 상태 전이가 정의되었는가(9장) — ASIL과 연계되는가 |
| ASIL별 설계 기법 | 안전 요구사항에서 파생된 ASIL 등급에 따라 필요한 설계 기법(예: 포인터/재귀/동적메모리/인터럽트 사용 제한)이 적용·문서화되었는가 |
| 아키텍처 검증 | 아키텍처가 일관성(내부 모순 없음), 완전성(모든 요구사항 할당), 정확성 관점에서 검토되었는가 |
| 요구사항 추적 | 안전요구사항을 포함한 모든 SW 요구사항이 아키텍처 요소에 빠짐없이 할당되었는가(12, 14장) |

미충족 항목은 "미충족"으로 명시하고, 재설계 또는 보완 조치를 권고사항으로 제시한다. 존재를 가정하거나 임의로 충족 처리하지 않는다.

## 보고 원칙

- 실제 산출물(파일/섹션)을 열어 확인한 근거만 인용한다. 파일명·존재 여부만으로 판단하지 않는다.
- 산출물이 없거나 확인 불가능하면 "부재/미확인"으로 명시한다.
- 자체 점검 결과는 사용자가 사용한 언어(기본: 한국어)로 작성한다.
