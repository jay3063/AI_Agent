# SW 시스템 테스트 케이스 생성

## 개요

SW 요구사항 명세서 기반으로 SW 시스템 테스트 케이스를 생성하기 위한 방법론 스킬입니다. 이 스킬은 "무엇을 근거로, 어떤 기법으로, 어떤 원칙으로" 테스트 케이스를 설계할지에 대한 방법론만 정의합니다. 요구사항 분석, 사용자와의 확인, 실제 산출물(xlsx) 작성은 이 스킬을 사용하는 에이전트(예: `sw-system-tester` 서브에이전트)가 수행합니다.

이 스킬을 로드할 때 `test-design-techniques` 스킬도 함께 로드합니다 — 테스트 케이스 설계 기법의 명칭·정의는 그 공통 카탈로그를 따르며 이 스킬에서 재정의하지 않습니다.

## 기반지식

- **ISO 26262 Part 6**: 소프트웨어 단위/통합/시스템 테스트에 대한 요건. 특히 ASIL 등급이 할당된 요구사항은 판정기준의 전 분기(경계값, 조건 조합)를 빠짐없이 검증해야 합니다.
- **A-SPICE SWE.4, SWE.5, SWE.6**: 소프트웨어 단위 검증, 통합 시험, 시스템 시험에 대한 Base Practice. 양방향 추적성(요구사항 ↔ 테스트 케이스)과 표준화된 시험 절차를 요구합니다.
- **ISO 29119 및 ISTQB**: 테스트 시나리오·테스트 케이스 설계 프로세스와 용어 체계(긍정/부정 분류 등)의 근거로 사용합니다.
- **ISO 25000 (SQuaRE)**: 비기능(품질) 요구사항을 분류하는 기준입니다. 비기능 테스트 케이스는 이 표준의 품질 특성(예: 기능적합성, 성능효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성)별로 그룹화합니다. 이 품질 특성 분류는 `requirements-analysis` 스킬이 비기능 요구사항 작성 시 사용하는 `references/iso25010.md`와 동일한 분류를 사용한다 — 요구사항에 태깅된 품질특성과 시스템 시험의 그룹화 기준이 어긋나지 않게 한다.

## 적용 대상 테스트 기법

기법의 명칭·정의는 이 스킬에서 재정의하지 않습니다. **`test-design-techniques` 스킬(공통 카탈로그)을 그대로 사용합니다** — `tdd`, `integration-testing` 스킬도 동일한 카탈로그를 참조하므로, 단위/통합/시스템 전 레벨에서 기법 명칭이 일관됩니다.

요구사항의 성격에 맞춰 카탈로그의 기법 중에서 선택해 적용하고, 각 테스트 케이스의 "사용 기법" 항목에 실제로 적용한 기법(카탈로그 표기 그대로)을 명시합니다. 시스템/자격시험 레벨에서는 요구사항분석 기반(기본), 동등분할, 경계값분석, 결정테이블, 상태전이, 조합/페어와이즈, 오류추정/경험기반, 엣지 케이스 분석을 모두 적용 대상으로 삼습니다(카탈로그의 "레벨별 적용 매트릭스" 참고).

## 작성 원칙

- 의미 없이 테스트 커버리지 수치 달성만을 목적으로 하는 케이스는 생성하지 않습니다.
- 테스트의 예상 결과를 임의로 가정하지 않습니다. 명세서에 근거가 없다면 이 스킬을 사용하는 에이전트가 사용자에게 확인을 받아야 합니다.
- 프로젝트에서 정한 테스트 커버리지 목표(예: CLAUDE.md에 명시된 기준)를 준수합니다.
- 실행자가 그대로 재현할 수 있는, 실행 가능한 테스트 케이스만 작성합니다.
- 기법 선택이나 커버리지 범위 설정이 판단하기 어려운 경우 임의로 결정하지 말고, 이 스킬을 사용하는 에이전트를 통해 사용자 검토를 받습니다.
- 명세서에 직접적 근거는 없으나 QA 관점에서 추가를 제안하고 싶은 테스트 케이스는 테스트 케이스명 끝에 "(제안)"이라고 표시해 구분합니다.
- 사용한 테스트 설계 기법을 각 케이스에 명시합니다.

## 도구 사용

- 페어와이즈/전수 조합 생성 절차(PICT 사용법)는 `test-design-techniques` 스킬의 "PICT를 이용한 조합/페어와이즈 테스트 생성" 절을 따릅니다. 이 스킬에서 별도로 정의하지 않습니다.

## 산출물 구조

- 기능 요구사항에 대한 테스트 케이스: "테스트 케이스" 시트
- 비기능 요구사항에 대한 테스트 케이스: 별도의 "비기능 테스트 케이스" 시트, ISO 25000 품질 특성별로 구분
- 요구사항 원문에 없거나 원문보다 엄격하게 사용자 확인을 거쳐 확정한 판정기준: "확정 근거" 열에 확정 일자와 승인 주체 기록

## 경계 (이 스킬이 다루지 않는 것)

- **테스트 베이시스는 SW 요구사항 명세서뿐이다.** 아키텍처 설계서의 컴포넌트/인터페이스 구조, 상세설계의 함수/모듈 구조는 참조하지 않는다 — 블랙박스 관점을 유지한다. 내부 구조가 필요한 시험(컴포넌트 간 상호작용, 인터페이스 계약)은 `integration-testing` 스킬(`integration-tester` 에이전트)의 몫이다.
- **함수 계약 단위의 화이트박스 검증은 다루지 않는다.** 그것은 `tdd` 스킬(`coding` 에이전트)의 몫이다.
- **구조적 커버리지(함수/Call 커버리지, statement/branch 등) 수치를 목표로 하지 않는다.** 이 스킬의 커버리지 기준은 "모든 SW 요구사항(기능+비기능)에 최소 1개 이상의 실행 가능한 케이스가 있는가"이며, 구조적 커버리지는 다루지 않는다.
- **이 스킬은 케이스 설계까지만 다루며, 실행은 다루지 않는다.** CLAUDE.md 시스템 테스트 지침의 "테스트 성공률 100%"는 이 케이스들이 실행된 뒤 평가되는 지표다 — 이 스킬/에이전트는 실행 가능한(재현 가능한) 케이스를 만드는 것으로 그 전제를 충족시키며, 실제 실행·Pass/Fail 판정은 이 스킬의 범위 밖이다(실행 주체가 별도로 필요하다는 뜻이며, 프로젝트에서 이를 어느 에이전트가 맡을지 아직 정해지지 않았다면 사용자에게 확인한다).
